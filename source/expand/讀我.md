## Introduction

The `expand` system is built to receive a series of PTokens and then emit a series of PTokens. Between receiving and emitting, it will replace any general or parameter entity reference tokens with added PTokens derived from the declarations for those entities.

Philosophically, The `expand` system is a neutral processing stage in the overall process of document handling. That is, it does no well formedness or validation checks. In fact, it strives to impose as little "correctness" checking on the series of PTokens as possible. This means that if, for example, a parameter entity reference PToken is received, this will expand it even if it is, logically, in the content part of the document.

Finally, this may emit entirely new tokens, such as errors that result from trying to retrieve external entities that can not be found, as well as some ElidedEntityDeclarations that are useful for later processors to evaluate information that otherwise lost through the entity expansion process.

## Entities

An entity is a unit of data that is involved in an XML document. It is easiest to think of an entity as a file of data. However, by design entities can be stored and retrieved from anywhere.

Let's enumerate the different entities

1. The main XML document (the one that starts with `<?xml version=... ?>`) is an entity (called the Document entity (§4.8)).
2. The external DTD subset, if it exists, is an entity (§2.8).
3. Parsed general entities. These are assumed to have text that can be processed by the XML processor.
4. Unparsed general entities. These may contain some other kind of information (e.g. an image).
5. Parameter entities. These are always parsable, but are used in a different context than general entities can be used.

General (parsed and unparsed) and parameter entities must be declared in the document DTD. Which means that each one is named with a `<!ENTITY ... >` declaration.

Parsed general and parameter entities can be referenced from particular places in the document. The references act like an inline "include" operation.

Parsed general entites are referenced like `&name;`. These can appear in the content of the XML document (after the first element start tag), in element attribute values, or in ATTLIST default values in the DTD.

Unparsed general entities can be referenced like `<elementName attrname="name"` in some element attributes.

Parameter entities are referenced like: `%name;`. These references can appear in certain places in the DTD (including in the declared value of some general entities and parameter entities), and in the content of any external parameter values (see  below).

General and parameter entities can be declared in the internal DTD subset or in the external DTD subset. You might call these internally declared and externally declared.

The value of a general parsed or parameter entity can be what the spec calls "internal" or "external". Confusingly, unlike the declaration location, this has nothing to do with which DTD subset they are declared in. Instead, it indicates whether the value of the entity is found directly in the internal or external DTD subset (`<!ENTITY foo "my value">`), or is stored elsewhere (generally another file). Thus, it is possible to have an external entity that is internally declared. Because that makes my brain hurt, this document will tend to use the word "value-internal" and "value-external".  

## Expansion

Entity expansion is the heart of what makes full XML conformance a challenge. The rules around handling entities are surprisingly nuanced, and their combination can lead to some surprises. It is possible to repeatedly read the spec and still misinterpret the rules.

The easiest way to think of expansion is replacing entity references (`&foo;` and `%foo;`) with the text from the respective entity declaration.

It is useful to think of there as being eight different kinds of entity expansion that can happen:

1. Expansion of the external DTD subset
2. Expansion of parameter entity references in the DTD
3. Expansion of parameter entity references in the values of internal parameter or general entities (what this author calls "value-internal entities") 
4. Expansion of parameter entity references in the values of external parameter entities ("value-external" entities)
5. Expansion of parameter entity references in the non-EntityValue portion of markup declarations
6. Expansion of general entity references in default values of ATTLIST declarations
7. Expansion of general entity references in element start or empty element attribute values
8. Expansion of general entity references in the content of the document.

"Expansion" involves two processes.  When a reference to an entity is encontered, the "replacement text" (discussed below) for that entity is constructed (rt construction), then that replacement text is parsed (rt parsing) at the location that is is encountered as if it had originally been at that location in the document. 

What is the replacement text? Full details are in §3.3.3).  It depends on a couple minor factors.  To get started in your understanding, for the entity "foo", `<!ENTITY foo "my text">`, the replacement text is "my text".

There are a couple details to be aware of, though:

#1: Value-external entities have the (optional) text declaration (`<?xml version="1.0" ... ?>`) removed from the entity value.

#2: Value-internal entities have character references replaced by the referenced character, and have any parameter entity references replaced by the relevant parameter entity value. The need for this, in particular the need for the character reference replacement is baffling at first, but it actually has its use. This will be explained below.  To make this concrete, given the following:

   ```
   <!ENTITY % pe1 "my text">`
   <!ENTITY ge "&#65;n example of %pe1;">`
   ```

the replacement text for the entity "ge" is "An example of my text".  To repeat: this replacement of character references and parameter entities does not happen if the value is external. Thus, if an value-external entity had this value:

   ```
   &#65;n example of %pe1;
   ```

it's replacemet text would be "&#65;n example of %pe1;".  Since our example here is that this is for a general entity, then the apparent parameter entity reference to pe1 would actually never be expanded, and so the literal characters "%pe1" would be part of the attribute or content of the document.

Once you have assembled the repacement text, that text will then be parsed at the point in the document that it was referenced, just as as any other text at that point in the input stream is processed.   Let's look at those seven cases again to see:

1. The external subset logically comes after the internal subset (#REF#), but still within the DTD.  So, its text is processed like any other part of the DTD (markup declarations are recognized, element starts are errors, etc). Any parameter entity references in that text will be expanded at the moment they are encountered (see 2-4).

2. If a parameter entity reference is found in the DTD (but not between the `<!` and `>` of any markup declarations) it is immediately replaced with the replacement text of the referenced entity. This does mean that if the declaration hasn't yet been encountered by the processor, it is an error. Unlike the other markup declarations, there are no "forward references" allowed here.  Note that just like the expansion of the external DTD subset, the replacement text of the parameter entity may contain other parameter entity references, which will be covered by cases 2-4 here.

3. A value-internal general or parameter entity may have a parameter entity reference in its value.  However, if an entity is declared in the internal subset and is value-internal, then it may not have a parameter entity reference in its value. Put another way, you can have a parameter entity reference in a value-internal entity declaration in the external subset, or you can have a parameter entity reference in a value-external parameter entitity. (if those characters are in a value-external general entity, they will not be processed as a parameter entity reference).  These references will be expanded immediately upon encountering them.  And since such a parameter entity value may, itself, contain parameter entity references, those will be expanded immediately as well. Again, this processing model makes any kind of "forward reference" impossible.

4. A parameter entity reference may also be found in the external value of another parameter entity reference. This will be expanded as soon as the associated parameter entity is referenced (that is, if parameter entity A has a reference to B in its external value, then when %A; is encountered, that external entity value will be read in, and parsed, which in turn will cause B to be expanded). As is always the case with entity references, the declaration must already have been encountered by the parser.

5. Parameter entity references may occur at other places in the markup declarations. e.g. `<!ELEMENT %moreElementData;>`. These are expnded, like #3, immediately at the point of encountering them (no forward references). The spec does require that these references should behave as if there is a space inserted before and after the replacement text in these uses, which does mean you can't do this: `<!%moreElementData>` (since one is not allowed to have a space after the `!` and before `ELEMENT`).  As far as this author can tell, however, any and every other portion of the markup declaration can be inserted by way of a parameter entity reference.  Like case #3, however, this can not happen in the internal subset.

6. Interestingly (and in the estimation of this author, another slightly surprising aspect of this processing model) a general entity reference found in an ATTLIST attribute default value is expanded immediately at the point of encountering the ATTLIST. It is worth thinking about this a bit more. the referenced general entity could be value-internal or value-external, and the declaration must have already been encountered by the processor.  If it is value internal, then that value will already have had any parameter entity references expanded (by #3). If it is value-external, anything that looks like a parameter entity reference will simply be treated like text.  At this point, this is processed like an attribute value (#6).

7. When an attribute is encountered, it may contain general entity references (anything that looks like a parameter entity reference will be treated as just text). The value of the entity will be treated like normal attribute value text, which means things like start tags, parameter entities, etc will be treated as just text (though, technically, it is not legal to have `<` directly in an attribute value). It IS possible (through the use of character references) to get something that looks like a parameter entity being processed at this point, but again it will be ignored.  However, any general entity references in the general entity replacement text will be expanded.

8. When a general entity is encountered in the content of the document, but not in an attribute value, it is processed like any other content (e.g. start tags will be recognized). This does mean things like any text that looks like a parameter entity reference will be treated as text.  Naturally, if there are general entity references in the general entity replacement text, they will then be expanded when encountered.

One way this author thinks of this is that every value-internal entity value (not in the internal subset) may have any number of trees of parameter entity expansion contributing to it. The DTD may have trees of parameter entity expansion appearing at any point, and individual markup declarations (in the external subset or value-external parameter entities) may as well. Those trees may contain value-internal and value-external parameter entity values. ATTLSIT default values, attribute valued and content may have trees of general entity values expandding from them (and those general entity values may be composed of text and parameter entity values)> 

### EXAMPLES

Two final details are worth mentioning:

1. At any given point of expansion, it isn't legal for a visible syntactic construct to cross entity boundaries.  That is, if you have a general entity like
   ```
      <!ENTITY foo "&abcd">
      <!ENTITY bar "efgh;">
   ```
Even if you do `&foo;&bar;` in the content, this will not result in a reference to `&abcdefgh;` at the point of processing. Instead, when `&foo;` is encountered, an error will be reported because the general entity referenced in there must have been complete.

2. Character references can be used in some interesting ways, however. consider this:
   ```
      <!ENTITY foo "&#38;#38;#38;">
   ```
In this example, the replacement text for foo is `(&)#38;#38;`.  Where the `(&)` indicates that this is a result of a character reference. When used in the document, the "(&)#38;" will be interpreted as `&`, followed by the characters `"#38"`.  This will not be interpreted as a character reference, but instead just as a series of 5 characters that looks like a character reference.

This gets even more interesting with escaping the `%` of a parameter entity reference. Because these involve an added processing step, 
   ```
      <!ENTITY % abcd "hi">
      <!ENTITY % part1 "&#38;#37;ab">
      <!ENTITY % part2 "cd;">
      <!ENTITY % constructed "%part1;%part2;">
      <!ENTITY final "%constructed;">
      ...
      <start>
      &final;
`   ```
This expands to
   ```
   <start>
   hi
   ```

The replacement text for `part1` is `(&)#37;ab`.  When `constructed` is expanded, we get `(%)abcd;`  When `final` is then expanded, its replacement text is `hi`.

## Implementation

As noted at the beginning, the expansion system makes almost no assumptions about the correctness of the tokens it receives. It simply processes each token it gets, as discussed below.  The one exception to this is that it does notice when it is in the internal subset, when it is processing the external subset, and when it is in the content of the document. There are certain expansion cases where this can not make the correct decisions without that knowledge.

This also honors the "validating" flag that it is passed. If that is true, this will load no value-external entities. If there are references to those, this will leave them reference tokens unexpanded.

### Inline expansions

For cases #1 (external DTD subset), #2 (parameter entity references between markup declarations) and #8 (general entity references in the content), this starts parsing those entity values and sending their contents through iself.  That is, if the EntityExpander receives a general entity reference (case #3) it will not acknowledge that token immediately, calling another routine which will retrieve the entity value, parse it and pass those tokens each though the EntityExpander itself, in what seems rather like a recursive call to itself.  From the caller's perspective it has just sent A, B and is waiting to send C (where B is an entity reference). But on the receiver's standpoint, it receives A, B, x1, x2, x3, x4 (where x1-x4 are the tokens that come from parsing the entity value of B.

### Within markup expansions
The other five expansion cases all involve expanding references that occur within particular markup tokens. In this case, when one of these tokens is encountered, all the processing necessary to expand the references in the entity value, markup declaration, attribute values or attribute list default values happens entirely to that token before it is passed onto the receiver.

At this time, if any entity value or attribute value would expand to a value larger than memory, this will fail.

### protoReplacementText

To make the within markup expansions work, EntityExpander keeps a store of all the value-internal entity declarations, and any value-external entity declarations needed to populate other entity declarations. This store keeps the "proto replacement text" for each declaration. This is called the proto replacement text because it isn't the original entity value, nor the final replacement text, but something between.

When a value-internal entity declaration is encountered, its value will already have had parameter entity references and character references parsed. Thus

1. `<!ENTITY % example "&#65; foo %bar; &baz;">`
 
 will arrive here with its value in a form like this, where the ()'s indicate a char or entity reference, and the rest is just text.

2. `(A) foo (ref(bar)) &baz;`

Entity expander will then look up the proto replacement text for the parameter entity `bar` (loading it from an external source if needed), parse that, and insert it at this point, leaving us with
3. `(A) foo (start(ref(bar)))bar text(end(ref(bar))) &baz;`

What that is attempting to show is that there are start and end markers inserted into the proto replacement text, along with the parsed content from `bar`.

This is proto replacement text, because it still has structure in it that is not the final replacement text.  That would be, in this case:

4. `A foo bar text &baz;`

#### Emergent references

Generally an entity value will simply have text, char refs and start/end markers in it. Generally, each successive parameter entity reference throws away a lot of that proto information.  That is, if that `example` entity were referenced in another entity value:

5. `<!ENTITY % anotherExample "[%example]">`

Its proto replacement text would be the following.

6. `[(start(ref(example)))A foo bar text &baz;(end(ref(example)))]`

Note that the start and end markers for `bar` have vanished.  That is, we do not get `[(start(ref(example)))(A) foo (start(ref(bar)))bar text(end(ref(bar))) &baz;(end(ref(example)))]`, since we actually have to parse the value of `example` in a way that doesn't allow us to be able to preserve the internal structure.

This next example helps to show why, and shows how entity references can "emerge" through repeated entity references.
   ```
   <!ENTITY % one "one">
   <!ENTITY % twoA "&#38;#37;on">
   <!ENTITY % twoB "e;">
   <!ENTITY % three "%twoA;%twoB;">
   <!ENTITY % four "%three;">
   ```
Note that the replacement text for `three` is `(%)one;`. That is, it almost looks like a parameter entity reference, but isn't quite because the `%` is still escaped.  But when `four` is expanded, it will briefly look like the following:

7. `(start(ref(three)))(ref(one))(end(ref(three)))`

which is then expanded into the proto replacement text

8. `(start(ref(three)))(start(ref(one)))one(end(ref(one)))(end(ref(three)))`

I refer to these as "emergent references" since through a series of character references, you can get a reference that appears in one level of the processing that wasn't there before.

### Elided declaration values

Because of all the preocessing mentioned above, the structure of value-external entities involved in constructing entity values and attribute values will get thrown away by the expansion process.  Yet, some of this information may be important to subsequent phases.  Thus, the EntityExpander will introduce `ElidedEntityDeclarationPToken` tokens into the stream that it passses on to the receiver. Each of these contains the entity value for any value-external entity declarations that is otherwise lost in the processing.

### Recursion (§4.1.0)
This blocks recursive expansion in four places. The wellformedness checks are done elsewhere. These checks are done in different places because of the different kinds of expansion that can happen.

For document "inline" expansion (that is, a GE or PE reference in the DTD or content), these checks are done in EntityExpander itself in `handleEntityReference()`.

A second place is in `expandAttributes()` to make sure that we don't end up making recursive calls to general entity references in this.

The third is in `expandEntityValue()`, to prevent an infinite expansion of parameter entity references.

The fourth is in `expandUnassigned()`, which also prevends infinite expansion of parameter entity references.

It is theoretically possible to end up with recursive expansions across these boundaries. For example, an attribute might be in a start tag that was introduced into the document by the replacement text of a general entity reference that is, itself, referenced, in the attribute.  This will catch such cases and report on them.

### Standalone documents
Standalone documents are a special case that has only limited impact on expansion, but it is worth keeping in mind.

It is possible to mark a document as "standalone" (`<?xml version="1.0" standalone="yes'>`). Intuitively, this means that the author of the document is promising that you can just read the document entity, load no external entities (including no external subset) and you will still be able to fully and accurately process the document. Intuitively, you'd also think this would mean that the document content is fully contained in the document entity, but this latter interpretation is not right.

More precisely, by §2.9.0, a standalone document has no markup declarations in the external subset or in parameter entities. 

In practise, when you process a standalone document, you are assured that you will be able to interpret the document correctly, which means you'll know the types of all the attributes, know when to ignore whitespace, etc. It does NOT, however, mean that you are asssured of having all the document content at the end of the processing.  That is, a standalone document may stil have relevant content in a value-external general entity.

Thus, "standlone" really is a comment on the syntactic processing of the document and limits on the DTD, and has no relevance to how complete the document is in the document entity.

What is likely your intuitive interpretation of "standalone" is more akin to saying that the document has no external entities. However, there is no formal way to declare that.

> Validity constraint: Proper Conditional Section/PE Nesting

If any of the "<![", "[", or "]]>" of a conditional section is contained in the replacement text for a parameter-entity reference, all of them must be contained in the same replacement text.

Like the internal and external DTD subsets, a conditional section may contain one or more complete declarations, comments, processing instructions, or nested conditional sections, intermingled with white space.

If the keyword of the conditional section is INCLUDE, then the contents of the conditional section must be processed as part of the DTD. If the keyword of the conditional section is IGNORE, then the contents of the conditional section must not be processed as part of the DTD. If a conditional section with a keyword of INCLUDE occurs within a larger conditional section with a keyword of IGNORE, both the outer and the inner conditional sections must be ignored. The contents of an ignored conditional section must be parsed by ignoring all characters after the "[" following the keyword, except conditional section starts "<![" and ends "]]>", until the matching conditional section end is found. Parameter entity references must not be recognized in this process.

If the keyword of the conditional section is a parameter-entity reference, the parameter entity must be replaced by its content before the processor decides whether to include or ignore the conditional section.

In a document without any DTD, a document with only an internal DTD subset which contains no parameter entity references, or a document with " standalone='yes' ", for an entity reference that does not occur within the external subset or a parameter entity, the Name given in the entity reference must match that in an entity declaration that does not occur within the external subset or a parameter entity, except that well-formed documents need not declare any of the following entities: amp, lt, gt, apos, quot. The declaration of a general entity must precede any reference to it which appears in a default value in an attribute-list declaration.

Note that non-validating processors are not obligated to read and process entity declarations occurring in parameter entities or in the external subset; for such documents, the rule that an entity must be declared is a well-formedness constraint only if standalone='yes'.

Validity constraint: Entity Declared

In a document with an external subset or parameter entity references, if the document is not standalone (either "standalone='no'" is specified or there is no standalone declaration), then the Name given in the entity reference must match that in an entity declaration. For interoperability, valid documents should declare the entities amp, lt, gt, apos, quot, in the form specified in 4.6 Predefined Entities. The declaration of a parameter entity must precede any reference to it. Similarly, the declaration of a general entity must precede any attribute-list declaration containing a default value with a direct or indirect reference to that general entity.

Well-formedness constraint: Parsed Entity

An entity reference must not contain the name of an unparsed entity. Unparsed entities may be referred to only in attribute values declared to be of type ENTITY or ENTITIES.

Well-formedness constraint: No Recursion

A parsed entity must not contain a recursive reference to itself, either directly or indirectly.

Well-formedness constraint: In DTD

Parameter-entity references must not appear outside the DTD.

### 4.2.0 Entity Declarations

The Name identifies the entity in an entity reference or, in the case of an unparsed entity, in the value of an ENTITY or ENTITIES attribute. If the same entity is declared more than once, the first declaration encountered is binding; at user option, an XML processor may issue a warning if entities are declared multiple times.

### §4.5.0 Construction of Entity Replacement text
This discusses how to take an entity value and generate the text that will be placed into the document.  To summarize it:

- The quoted value in an entity declaration is the literal value of an value-internal entity
- The entire content of the external entity "file" is the literal value of a value-external entity
- the replacement text of the value-internal entity is literal value with character references replaced by the corresponding character, and parameter entity references replaced by the replacement text of the parameter entity.
- The replacement text of a value-external entity is the text itself (after removing the text declaration)

There are several things worth calling out here explicitly:

- value-internal entities essentially go through an extra phase of processing.  In this implementation, the values of value-internal entities are parsed for character references and parameter entity references at initial parsing time. Both kinds of entity values then get parsed again to look for general entity references.

- That the various references must be fully contained in the literal value (meaning, you can't have `&na` in one literal value and `me;` in an adjacent).

- Not super obvious, but external entities are not pre-parsed at all. Thus, if they contain a PE ref or a GE ref, that is only discovered at usage time, not in some kind of intermediate processing state. Put another way:
   - internal entities are processed, and have things fully expanded, and this results in the string that is then consumed when that entity is referenced.
   - external entities provide the string that is consumed when that entity is referenced. Thus, unlike internal entities, PE Refs are not recognized "specially".

 * This takes an AttributeValuePToken and expands all General Entity References and
 * character references in it, and returns a new one with all the expanded values.
 *
 * Entity processing is, for better or worse, the bane of dealing with XML. It is
 * made more complex by this project's decision to separate different kinds of
 * processing into different stages in a pipeline.  So, it is worth walking
 * through this in excruciating detail, both for you, dear reader, as well as
 * my own future self.
 *
 * First, the input AttributeValuePToken can only contain Text, CharRefs and GE Refs
 * in it (if, for some reason, an attribute value was passed through twice, then it
 * could also have GE Start and GE Ends, which does not significantly change the
 * algorithm here). Note that this AttributeValuePToken could be from the attribute
 * on an ElementStart or EmptyElement, or a default value in an ATTLIST attribute
 * declaration.
 *
 * The goal of this routine is to replace any GE References with a GE Start, the
 * contents of the corresponding GE declaration value, and a GE End. Since
 * this is part of the expansion stage in the pipeline, this does no error
 * reporting, but instead leaves enough information in the PTokens for other
 * stages in the pipeline to report fully.  The description below notes
 * where the error reporting should happen.
 *
 * First, of course, the GE Reference may not have a corresponding declaration.
 * In this case, this routine leaves the GE Reference in the AttributeValuePToken.
 * THis will generate well formed and/or validity errors in other stages
 *
 * Second, the GE Reference may reference an unparsed entity, which is illegal.
 * In this case we leave the GE Reference in the new AttributeValuePToken.
 * Other stages wil report an error
 *
 * Third, and "most" puzzling, the entity may refer to a value-external entity,
 * which is not allowed (this should not be confused with an externally declared
 * entity, which is fine). In this case, we will try to retrieve the value
 * anyway and insert the value. Other stages will report errors.
 *
 * Fourth, as noted below, we may be in the middle of a recursive call
 * to this routine, and we may find that we're about to start parsing a
 * GE Ref which we're in the middle of parsing higher up in the stack.
 * In this case we will simply leave the GERef in the results.
 *
 * Once we've found the entity, we then retrieve the EntityValuePToken from
 * another routine. We pass it enough information that it will not just return
 * the EntityValuePToken for that entity, but if necessary retrieve and insert
 * all parameter entities referenced from that General Entity declaration
 * value. Those parameter entities may, themselves, refer to other parameter
 * entities. That routine will try to accumulate all of these into
 * the EntityValuePToken it returns. It may encounter value-external entities
 * as well as recursive references to parameter entities, or simply missing
 * declarations. Value-external entities will nevertheless be inserted into
 * this if possible, while recursive entries and missing declarations will
 * leave the reference token in place.
 *
 * Once this gets the EntityValuePToken back, it then does several things
