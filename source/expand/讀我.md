An EntityExpander transforms a series of PTokens by replacing any
general or parameter entity reference tokens it receives (either
as tokens directly received, or embedded within entity declaration
values, attribute declaration list default values, other within
markup declarations, or in attribute values) with a series of
tokens from the corresponding entity values.

Philosophically, this sees itself as a neutral proessing stage in
the overall pipeline of XML document handling. That is, it does
not do any well formed or validation checks. However, for reasons
discussed below, to make this stance work, it will introduce
certain new tokens into the stream that are essentially metadata
for well formed or validation checks later on. Because it may
try to load external entities, and those loading processes may
fail, this may introduce some XML Error's into the stream.

## Expansion

Entity expansion is the heart of what makes full XML conformance a challenge. The rules around handling entities are surprisingly nuanced, and their combination can lead to some surprises. In the opinion of this author, it also takes some trial and error with other tools to clarify some details of the spec (e.g. discovering an unexpected bit of behavior in a tool, then re-reading the spec closely and saying "Oh! I wouldn't have interpreted it that way. Interesting!")

You can think of there as being eight different kinds of expansion that can happen:

1. Expansion of the external DTD subset
2. Expansion of parameter entity references in the DTD
3. Expansion of parameter entity references in the values of internal parameter or general entities (what this author calls "value-internal entities") 
4. Expansion of parameter entity references in the values of external parameter entities ("value-external")
5. Expansion of parameter entity references in the non-EntityValue portion of markup declarations
6. Expansion of general entity references in default values of ATTLIST declarations
7. Expansion of general entity references in element start or empty element attribute values
8. Expansion of general entity references in the content of the document.

An inaccurate, but useful, way to think about entity expansion is that when a parameter or general entity reference is encountered, the entity value is "inserted" into the document processing at that point. Essentially an "import" statement at the reference point.

However, this is actually more nuanced.  The text that is inserted into the document at the point of the reference may have been altered from what was in the original entity value. The standard calls this the "replacement text". The alteration are:

#1: Value-external entities have the text declaration (`<?xml version="1.0" ... ?>`) removed from the entity value.

#2: Value-internal entities have character references replaced by the referenced character, and have any parameter entity references replaced by the relevant parameter entity value. The need for this, in particular the need for the character reference replacement is baffling at first, but it actually has its use. This will be explained below.

Once you have done that processing, the text of the entity value is then processed as any other text at that point in the input stream is processed.   Let's look at those seven cases again to see:

1. The external subset logically comes after the internal subset (#REF#), but still within the DTD.  So, its text is processed like any other part of the DTD (markup declarations are recognized, element starts are errors, etc). Any parameter entity references in that text will be expanded at the moment they are encountered (see 2-4).

2. If a parameter entity reference is found in the DTD (but not between the `<!` and `>` of any markup declarations) are immediately be replaced with the replacement text of the referenced entity. This does mean that if the declaration hasn't yet been encountered by the processor, it is an error. Unlike the other markup declarations, there are no "forward references" allowed here.  Note that just like the expansion of the external DTD subset, the replacement text of the parameter entity may contain other parameter entity references, which will be covered by cases 2-4 here.

3. A general or parameter entity may have a parameter entity reference in its value.  However, if an entity is declared in the internal subset and is value-internal (that is, this is an internal entity in the internal subet), then it may not have a parameter entity reference in its value (# I assume this is to make non-validating processers have an easier time#). Put another way, you can have a parameter entity value in a value-internal entity declaration in the external subset, or you can have a parameter entity value in a value-external parameter entitity. (if those characters are in a value-external general entity, they will not be processed as a parameter entity reference).  These references will be expanded immediately upon encountering them.  And since such a parameter entity value may, itself, contain parameter entity references, those will be expanded immediately as well. Again, this processing model makes any kind of "forward reference" impossible.

4. A parameter entity reference may also be found in the external value of another parameter entity reference. This will be expanded as soon as the associated parameter entity is referenced (that is, if parameter entity A has a reference to B in its external value, then when %A; is referenced, that external entity value will be read in, and immediately parsed, which in turn will cause B to be expanded). As is always the case with entity references, the declaration must already have been encountered by the parser.

5. Parameter entity references may occur at other places in the markup declarations. e.g. `<!ELEMENT %moreElementData;>`. These are expnded, like #3, immediately at the point of encountering them (no forward references). The spec does require that these references should behave as if there is a space inserted before and after the replacement text in these uses, which does mean you can't do this: `<!%moreElementData>` (since one is not allowed to have a space after the `!` and before `ELEMENT`.  As far as this author can tell, however, any and every other portion of the markup declaration can be inserted by way of a parameter entity reference.  Again, the replacement text may, itself, have references to other parameter entities which are also expanded on the spot.  Like case #3, however, this can not happen in value-internal entity values in the internal subset.

6. Interestingly (and in the estimation of this author, another slightly surprising aspect of this processing model) a general entity reference found in an ATTLIST attribute default value is expanded immediately at the point of encountering the ATTLIST. It is worth thinking about this a bit more. the referenced general entity could be value-internal or value-external, and the declaration must have already been encountered by the processor.  If it is value internal, then that value will already have had any parameter entity references expanded (by #3). If it is value-external, then the processing model will not have pre-expanded any parameter entity values.  At this point, this is processed like an attribute value (#6).

7. When an attribute is encountered, it may contain general entity references (anything that looks like a parameter entity reference will be treated as just text). The value of the entity will be treated like normal attribute value text, which means things like start tags, parameter entities, etc will be treated as just text (though, technically, it is not legal to have `<` directly in an attribute value). It IS possible (through the use of character references) to get something that looks like a parameter entity being processed at this point, but again it will be ignored.  However, any general entity references in the general entity replacement text will be expanded.

8. When a general entity is encountered in the content of the document, but not in an attribute value, it is processed like any other content (e.g. start tags will be recognized). This does mean things like any text that looks like a parameter entity reference will be treated as text.  Naturally, if there are general entity references in the general entity replacement text, they will then be expanded when encountered.

One way this author thinks of this is that every value-internal entity value (not in the internal subset) may have any number of trees of parameter entity expansion contributing to it. The DTD may have trees of parameter entity expansion appearing at any point, and individual markup declarations (in the external subset or value-external parameter entities) may as well. Those trees may contain value-internal and value-external parameter entity values. ATTLSIT default values, attribute valued and content may have trees of general entity values expandding from them (and those general entity values may be composed of text and parameter entity values)> 

Another way this author thinks of it is: the text in a value-internal entity may be processed up to three times (!).  Once at the point of encountering the declaration. If it is a parameter entity then it maybe be processed again when it is used in a general entity value.  That final entity value will be processed again when it is used in an attrbute value (default or element start/empty) or the content. With character references used judiciously, you can end up with certain references "materializing" as this process happens.

Two final details are worth mentioning:

1. At any given point of expansion, it isn't legal for a visible syntactic construct to cross entity boundaries.  That is, if you have a general entity like
   ```
      <!ENTITY foo "&abcd">
      <!ENTITY bar "efgh;">
   ```
Even if you do `&foo;&bar;` in the content, this will not result in a reference to `&abcdefgh;` at the point of processing. Instead, when `&foo;` is encountered, an error will be reported because the general entity referenced in there must have been complete.

2. Character references can be used in some interesting ways, however. consider this:
   ```
      <!ENTITY foo "&#37;abcd">
      <!ENTITY bar "efgh;">
   ```
In this example, the replacement text for foo is `(&)abcd`.  Where the `(&)` indicates that this is a result of a character reference.When used in the document, however, the text that will appear in the document is `&abcdefgh;`, and it will not be interpreted as a general entity reference. Every general entity reference token that is encountered in the document content or in attribute values (or ATTLIST defaults) is "expanded" to a general entity start, followed by the parsed content of that entity, followed by a general entity end token.

The parsed content of the general entity may include the expansions of other general entity references. Thus:

```xml
<!ENTITY second "foo">
<!ENTITY first "a &second; b">
...
&first;
...
```

would expand to:

```
(start-first) (a ) (start-second) (foo) (end-second) ( b) (end-first)
```

## Internal behavior

### General entity declarations

When a value-internal general entity declaration is encountered, this will immediately expand the value, and store that expansion in an internal cache.

This internal expansion repalces all parameter entity references with their corresponding replacement text (which is to say, a series of text, char ref, parameter reference and parameter entity start and end tokens). This is done recursively, so that if there are any parameter entity references in the expanded parameter entity replacement texts, those are further expanded.  The only time a parameter entity reference is left unexpanded is if there is no declaration for it, or if a value-external could not be loaded, or if this is doing a non-validating processing, and the reference is to a value-external entity.

There is, of course, a risk that the resulting entity might be larger than available memory. This will ahve to be addressed in a future version.

Note that the implicit implication of this is that every parameter entity referenced must already have been declared earlier in the document.  No forward references are possible.  Also, to be explicit, each value-internal parameter entity declaration would already hve gone through a similar expansion process at the time their declaration was encountered.



ARCHITECTURE

This class, like the rest of this project, is deliberately built
to be neutral to how PTokens are delivered to it. Like the rest of
the system, this could be harnessed into something using node.js
strems to obtain and deliver tokens, or it could be ultimately
living in a browser with a different mechamism. Like the rest of
the system, this simply recieves tokens and uses a callback
scheme to signal that it is done processing that. This does not
use promises both because the system didn't use promises when it
was started, and because some experiments have shown that promises
can significantly drag the performance down since it requires a full
event loop cycle to get back to the work, and given the
"size" of the data flowing through this that can degrade performance
significantly. The downside to this is one must be sensitive to the
stack size that could emerge.

## Standard

### §2.2.0 Characters
- A parsed entity contains text which may represent markup or character data

### §2.3.0 Characters
- General entities should not contain only the literal "<" character (as opposed to a chara reference `&#60;`) because its use will be a well formedness error. 

> Although the EntityValue production allows the definition of a general entity consisting of a single explicit < in the literal (e.g., <!ENTITY mylt "<">), it is strongly advised to avoid this practice since any reference to that entity will cause a well-formedness error.

I think the reason for this goes back to the fact that general entity values must contain whole syntactic units.  In an attribute this is an error because "<" can not appear in an attribute. In the content, it would be an error because it is an incomplete syntactic unit.



### §4.5.0 Construction of Entity Replacement text
This discusses how to take an entity value and generate the text that will be placed into the document.  To summarize it:

- The quoted value in an entity declaration is the literal value of an value-internal entity
- The entire content of the external entity "file" is the literal value of a value-external entity
- the replacement text of the value-internal entity is literal value with character references replaced by the corresponding character, and parameter entity references replaced by the replacement text of the parameter entity.
- The replacement text of a value-external entity is the text itself (after removing the text declaration)

There are several things worth calling out here explicitly:

- value-internal entities essentially go through an extra phase of processing.  In this implementation, the values of value-internal entities are parsed for character references and parameter entity references at initial parsing time. Both kinds of entity values then get parsed again to look for general entity references.

- That the various references must be fully contained in the literal value (meaning, you can't have `&na` in one literal value and `me;` in an adjacent).

- Not super obvious, but external entities are not pre-parsed at all. Thus, if they contain a PE ref or a GE ref, that is only discovered at usage time, not in some kind of intermediate processing state. Put another way:
   - internal entities are processed, and have things fully expanded, and this results in the string that is then consumed when that entity is referenced.
   - external entities provide the string that is consumed when that entity is referenced. Thus, unlike internal entities, PE Refs are not recognized "specially".
