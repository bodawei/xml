## Introduction

The `expand` system is built to receive a series of PTokens and then emit a series of PTokens. Between receiving and emitting, it will replace any general or parameter entity reference tokens with added PTokens derived from the declarations for those entities.

Philosophically, The `expand` system is a neutral processing stage in the overall process of document handling. That is, it does no well formedness or validation checks. In fact, it strives to impose as little "correctness" checking on the series of PTokens as possible. This means that if, for example, a parameter entity reference PToken is received, this will expand it even if it is, logically, in the content part of the document.

Finally, this may emit entirely new tokens, such as errors that result from trying to retrieve external entities that can not be found, as well as some synthetic PTokens that are useful for later processors to evaluate information that otherwise lost through the entity expansion process.

## Entities

An entity is a unit of data that is involved in an XML document. It is easiest to think of an entity as a file of data. However, by design entities can be stored and retrieved from anywhere.

Let's enumerate the different entities

1. The main XML document (the one that starts with `<?xml version=... ?>`) is an entity (called the Document entity (§4.8)).
2. The external DTD subset, if it exists, is an entity (§2.8).
3. Parsed general entities. These are assumed to have text that can be processed by the XML processor.
4. Unparsed general entities. These may contain some other kind of information (e.g. an image).
5. Parameter entities. These are always parsable, but are used in a different context than general entities can be used.

General (parsed and unparsed) and parameter entities must be declared in the document DTD. Which means that each one is named with a `<!ENTITY ... >` declaration.

Parsed general and parameter entities can be referenced from particular places in the document. The references act like an inline "include" operation.

Parsed general entites are referenced like `&name;`. These can appear in the content of the XML document (after the first element start tag), in element attribute values, or in ATTLIST default values in the DTD.

Unparsed general entities can be referenced like `attrname="name"` in some element attributes.

Parameter entities are referenced like: `%name;`. These references can appear in certain places in the DTD (including in the declared value of some general entities and parameter entities), and in the content of any external values (see  below).

General and parameter entities can be declared in the internal DTD subset or in the external DTD subset. You might call these internally declared and externally declared.

The value of a general parsed or parameter entity can be what the spec calls "internal" or "external". Confusingly, unlike the declaration location, this has nothing to do with which DTD subset they are declared in. Instead, it indicates whether the value of the entity is found directly in the internal or external DTD subset (`<!ENTITY foo "my value">`), or whether the value is stored elsewhere (generally another file). Thus, it is possible to have an external entity that is internally declared. Because that makes my brain hurt, this document will tend to use the word "value-internal" and "value-external".

## Internal behavior

### General entity declarations

When a value-internal general entity declaration is encountered, this will immediately expand the value, and store that expansion in an internal cache.

This internal expansion repalces all parameter entity references with their corresponding replacement text (which is to say, a series of text, char ref, parameter reference and parameter entity start and end tokens). This is done recursively, so that if there are any parameter entity references in the expanded parameter entity replacement texts, those are further expanded.  The only time a parameter entity reference is left unexpanded is if there is no declaration for it, or if a value-external could not be loaded, or if this is doing a non-validating processing, and the reference is to a value-external entity.

There is, of course, a risk that the resulting entity might be larger than available memory. This will ahve to be addressed in a future version.

Note that the implicit implication of this is that every parameter entity referenced must already have been declared earlier in the document.  No forward references are possible.  Also, to be explicit, each value-internal parameter entity declaration would already hve gone through a similar expansion process at the time their declaration was encountered.

### Recursion (§4.1.0)
This blocks recursive expansion in fourth places. The wellformedness checks are done elsewhere. These checks are done in different places because of the different kinds of expansion that can happen.

For document "inline" expansion (that is, a GE or PE reference in the DTD or content), these checks are done in EntityExpander itself in `handleEntityReference()`.

A second place is in `expandAttributes()` to make sure that we don't end up making recursive calls to general entity references in this.

The third is in `expandEntityValue()`, to prevent an infinite expansion of parameter entity references.

The fourth is in `expandUnassigned()`, which also prevends infinite expansion of parameter entity references.

It is theoretically possible to end up with recursive expansions across these boundaries. For example, an attribute might be in a start tag that was introduced into the document by the replacement text of a general entity reference that is, itself, referenced, in the attribute.  This will stop these.

## Architecture
### Design principles
* Like the rest of the system, this uses callbacks to handle asynchronous calls, nor promises.
* While we use token types a lot in typescript definitions, the code relies on checking the type property. This is to allow for ducktyping of these objects, rather than instanceof
* At this time, some entity values are being kept entirely in memory. This is for values for internal entities, as well as any entities (internal or externally valued) used to build the replacement text for internal entities.  This may be a problem down the road, but reight not it is expedient

ARCHITECTURE

This class, like the rest of this project, is deliberately built
to be neutral to how PTokens are delivered to it. Like the rest of
the system, this could be harnessed into something using node.js
strems to obtain and deliver tokens, or it could be ultimately
living in a browser with a different mechamism. Like the rest of
the system, this simply recieves tokens and uses a callback
scheme to signal that it is done processing that. This does not
use promises both because the system didn't use promises when it
was started, and because some experiments have shown that promises
can significantly drag the performance down since it requires a full
event loop cycle to get back to the work, and given the
"size" of the data flowing through this that can degrade performance
significantly. The downside to this is one must be sensitive to the
stack size that could emerge.

### Standalone documents
Standalone documents are a special case that has only limited impact on expansion, but it is worth keeping in mind.

It is possible to mark a document as "standalone" (`<?xml version="1.0" standalone="yes'>`). Intuitively, this means that the author of the document is promising that you can just read the document entity, load no external entities (including no external subset) and you will still be able to fully and accurately process the document. Intuitively, you'd also think this would mean that the document content is fully contained in the document entity, but this latter interpretation is not right.

More precisely, by §2.9.0, a standalone document has no markup declarations in the external subset or in parameter entities. 

In practise, when you process a standalone document, you are assured that you will be able to interpret the document correctly, which means you'll know the types of all the attributes, know when to ignore whitespace, etc. It does NOT, however, mean that you are asssured of having all the document content at the end of the processing.  That is, a standalone document may stil have relevant content in a value-external general entity.

Thus, "standlone" really is a comment on the syntactic processing of the document and limits on the DTD, and has no relevance to how complete the document is in the document entity.

What is likely your intuitive interpretation of "standalone" is more akin to saying that the document has no external entities. However, there is no formal way to declare that.

> Validity constraint: Proper Conditional Section/PE Nesting

If any of the "<![", "[", or "]]>" of a conditional section is contained in the replacement text for a parameter-entity reference, all of them must be contained in the same replacement text.

Like the internal and external DTD subsets, a conditional section may contain one or more complete declarations, comments, processing instructions, or nested conditional sections, intermingled with white space.

If the keyword of the conditional section is INCLUDE, then the contents of the conditional section must be processed as part of the DTD. If the keyword of the conditional section is IGNORE, then the contents of the conditional section must not be processed as part of the DTD. If a conditional section with a keyword of INCLUDE occurs within a larger conditional section with a keyword of IGNORE, both the outer and the inner conditional sections must be ignored. Parameter entity references must not be recognized in this process.

If the keyword of the conditional section is a parameter-entity reference, the parameter entity must be replaced by its content before the processor decides whether to include or ignore the conditional section.

### §4.5.0 Construction of Entity Replacement text
This discusses how to take an entity value and generate the text that will be placed into the document.  To summarize it:

- The quoted value in an entity declaration is the literal value of an value-internal entity
- The entire content of the external entity "file" is the literal value of a value-external entity
- the replacement text of the value-internal entity is literal value with character references replaced by the corresponding character, and parameter entity references replaced by the replacement text of the parameter entity.
- The replacement text of a value-external entity is the text itself (after removing the text declaration)

There are several things worth calling out here explicitly:

- value-internal entities essentially go through an extra phase of processing.  In this implementation, the values of value-internal entities are parsed for character references and parameter entity references at initial parsing time. Both kinds of entity values then get parsed again to look for general entity references.

- That the various references must be fully contained in the literal value (meaning, you can't have `&na` in one literal value and `me;` in an adjacent).

- Not super obvious, but external entities are not pre-parsed at all. Thus, if they contain a PE ref or a GE ref, that is only discovered at usage time, not in some kind of intermediate processing state. Put another way:
   - internal entities are processed, and have things fully expanded, and this results in the string that is then consumed when that entity is referenced.
   - external entities provide the string that is consumed when that entity is referenced. Thus, unlike internal entities, PE Refs are not recognized "specially".

## 4.6.0 Predefined entiteis

> [Definition: Entity and character references may both be used to escape the left angle bracket, ampersand, and other delimiters. All XML processors must recognize these entities whether they are declared or not. For interoperability, valid XML documents should declare these entities, like any others, before using them. If the entities lt or amp are declared, they must be declared as internal entities whose replacement text is a character reference to the respective character (less-than sign or ampersand) being escaped; the double escaping is required for these entities so that references to them produce a well-formed result. If the entities gt, apos, or quot are declared, they must be declared as internal entities whose replacement text is the single character being escaped (or a character reference to that character; the double escaping here is optional but harmless).  * algorithm here). Note that this AttributeValuePToken could be from the attribute
 * on an ElementStart or EmptyElement, or a default value in an ATTLIST attribute
 * declaration.
 *
 * The goal of this routine is to replace any GE References with a GE Start, the
 * contents of the corresponding GE declaration value, and a GE End. Since
 * this is part of the expansion stage in the pipeline, this does no error

 * stages in the pipeline to report fully.  The description below notes
 * where the error reporting should happen.

 * In this case, this routine leaves the GE Reference in the AttributeValuePToken.
