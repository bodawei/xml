M: 207 Encodings
This is encodings draft 2.
The basic plan is this:
1) TokenSource has an encoding option. When specified, it overrides everything. If it causes a barf, its on you. (and a version option)
2) ChunkSource will examine the first bytes of the first segment. It can identify certain encodings.  If it can identify one with certainty, that will "win"
3) It will look at the first segment(s) to find the xml or text declaration.  If present, it will extract the version (defaults to 1.0/5 if not found) and the encoding.  If no other encoding specified or discovered, this will be used.  If #2 identified an ambiguous encoding, and this does not contradict that, then this wins.

0) (out of scope here) entity manager can have an encoding and version specified on a per entity basic (public? identifier).  Allowing you to override the default.
a) ChunkSource accepts version: can be 1.0 or 1.1. Anything else is failure.
b) ChunkSource accepts an encoding.
c) ChunkSource has a peek extractor that will scan the bytes and identify  Only called if we haven't already been given an encoding.
	UTF-16BE-LE/BOM's:
	UTF-16BE-LE/no BOM: 
	UTF-8 with the <? bit
	UCS-4 variations
	EBCDIC
	Finding <?xm  puts us in the possibly-unencoded
	If found, these are all decisive.  But, they may not be found.in which case we fall back to 'perhaps-unencoded'
		We could possibly do other things to identify UTF-16 better
d) Caller can make a call asking if there's a BOM on UTF-16.  This will return a simple value. Is async, and can be called first

We can now do conversion, if the type is known.

e) ChunkSource has a peek extractor that finds the <?xml ?> section in the first hundred bytes or so. and extracts version and encoding.  Doesn't call if have both an encoding and a version. Will ignore the value of either if have one of them.
	If encoding contradicts what we already have, ignore it.
	If encoding is a specialization (e.g. was perhaps-unencoded, but this is not one of ones we could be decisively identifying) then we use it.

In any case, we have enough information for conversion at this point:
- c might be a buffer or string
	- string_decode seems nice, but doesn't even do the minimum character sets (e.g. UTF-16BE)
	- https://github.com/bnoordhuis/node-iconv will do a bunch and stream. Throws error on bad. Can handle streaming
	- https://github.com/ashtuchkin/iconv-lite claims better speed.  Silently corrupts if bad characters. not clear about streamed

A: entity manager has a mapping of system literal (url) to encoding/version info. Will pass to chunksource
B: ChunkSource accepts an encoding and version. Sets internally as determinedEncoding/Version
C: If no encoding, calls (autonomous) routine with first 4+ bytes/chars: returns either a decisive value or "i dunno"  Sets decisive value or none.  This requires a peeking extractor to get this info.  Is set up at construction time
D: If we have a decisive value at this point, convert the segments that exist, and each as it comes in.
E: A peeking extractor will pull out the <? ... ?> string, unless we already have both decisive values. Extracts version and encoding using regex. If we can't find these (due to malformed) such is life. Document and move on.
F: Hereafter we decode each.  We use a default decoder (probably iconv-lite), but you can provide aanother. This may be very async as that thing may return a stream (in fact, maybe it always should, even if there's no stream there)
