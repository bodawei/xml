Design
	call a routine
		if we can find to the end, return
		if we can't find but plenty of text, return failure
		if we can't and at buffer end and buffers done, return failure
		if we can't, but at buffer end and more buffers coming
			(optimize: if our matched-so-far bit is small enough, substr it from buffer so we can gc)
			store operation, if match store offset within matched value
	when buffer arrives:
		push buffer
		if in middle operation, then try to continue with above algorithm.
			may fail to find a match (return with failure)
			may find a match or end of extension (return the data, and discard buffer(s))
			may consume buffer but not fully find match or extend-end, in which case push and continue

* I think we can reduce all chunks to just one kind.  Esentially the WithSpaceChunk.
* One can ask for only digits, but the parsing of them as hex or decimal and making an integer out of them can happen at higher levels
* Chunks can have start offset, end offset, and an optional array of mid-offsets
* The entity value cursor
    * will assemble the entity value into a single string, pass to the string cursor (see below) probably with a ‘don’t generate chunks’ flag.  And as values come back, it just reconstructs the relevant offsets from its set of tokens and the cursor’s chunks.  Pretty easy to do EXCEPT for whitespace.  Because what comes out of it is a single chunk, it can still combine the original values and final values ok, but won’t return the original chunks.
* async cursor
    * actually, very simple. We augment the original cursor so it can take a string and a “is this all” flag.  If it isn’t all and it can not decisively complete what it is doing, then it won’t return.  it will instead wait for the next chunk to arrive.
    * So, the async cursor is really just a stream to cursor translator
    * We still can’t make the cursor itself drive what to push out as chunks, since depends on context
        * But more and more I wonder if we can define the context well enough that it could make these decisions itself.
* alternate token streams
    * We need an entiyValue to both an attribute value and an entity value stream.  The difference is just which things it recognizes.  We could do a single one which takes a flag of which to pay attention to: % or &# or &.
    * This sounds a lot like our quoted value thing.  I wonder if we could somehow combine this. yet, this ends up in a stacked case, making this sound suspiciously like the entity stream.
