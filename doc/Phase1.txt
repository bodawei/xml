Async
-----
- Sooner or later, we need to be able to do parsing async.  We actually should be able to be living off of streams. Part of the goal of this to be generating a stream of tokens is to allow, like SAX, to handle files bigger than memory.
	XmlTokenStream should have something like:
		getNextToken(callback)
		and/or a node style .on() kind of pattern
	or, perhaps we should do
		getNextToken():Promise
	RAther than every cursor call involving a callback (which would make some of the parsing routines really ugly), I would imagine a cursor may change to just take a series of instructions:
		[
			{'name', 'word', '>'},
			function(results, continue) {
				if (results.name && results.name.text === '%') {
					results.isParameter = true;
					continue([{ 'post%Space', 'space'}, { 'name', 'word'}]);
					return;
				}
				continue();
			},
			{'postNameSpace', 'space', '>'}
			...
		}
	That is, to describe the multiple calls, with some occasional logic checks. In this way the async can be pulled largely into the cursors.
	TokenStream then contains a main decision making loop, and whenever it gets an answer from the cursor, it validates, builds a token, and pushes, which will then trigger an async call back.
	For the .on() to work, the token stream must always have descriptors queued in the cursor, since the cursor by itself can not parse the text.  (the cursors do really stop being cursors at this point)
	We really can fake this at this point by having the toplevel getNextToken(callback) call at this point, but we'll have to do a settimeout() of 0 here, or we'll end up with a very deep stack.
	Note, however, that this transition will touch most tests, making this an expensive api change.

And the bit that I've been doing the wishful thinking saying "well, we'll be able to transition over to async in the parsing/validation layer pretty easily" was more and more clearly not goign to be that simple. This left my project in what I felt was a really bad state.  This was a place where the whole thing could collapse on me.  That is, the obvious paths forward were:
* Abandon ChunkSource for now and get the rest done and deal with async after 1.0
* Bite the bullet and push the async back up the stack
And both were ugly and expensive.
In addition, I still wanted to get something done to show at Silicon Valley Code Camp. #1 wasn't going to do that well for me.  The mixed async and sync behavior was ugly, and really doing some of the entity expansion was just weird with cursors being sync and the entity expansion not.  Yes, I could bridge this by gathering all the async from some external stream, deliver that to the sync stream, which would work with Expension, but it would not be something I'd be proud to be showing.
So, I decided to spend a week or two and finish Chunk Source and see what would the cost be of doing #2.  Call it a exploratory diversion.
While I was finishing up ChunkSource (which I'm reasonably happy with at this point) I learned that SVCC was going on a more limited thing this year. highly doubtful I could make my presentation anyway.  So, that kinda took away some time pressure. Though, I would like to get this damn thing done.

Yesterday and Today (having finished chunk source well enough on Sat), I started to explore what it would take to do the upper levels on top of ChunkSource.  I did a rough sketch of three solutions:
a) One involving callbacks
b) One involving promises and async/await
c) A third option, introduced as I was looking at the promises one, which does callbacks differently.
It turned out (a), which was the solution that has been in my mind for months, was really more cumbersome than I expected.  The example was 200 lines long and the callbacks from callbacks was hard to understand.
(b) was surprisingly short and easy to understand.  About 90 lines
(c) surprised me by being about 100 lines, and while more cumbersome to understand than (b), much better than (a).
I really wanted to do performance measurement of these to compare and contrast. A test run on jsperf showed me that creating Promises were dramatically slower than I would have expected. However, I then ran into the "usual" fight with babel and the build system. getting a non-babelized async/await solution in place was going to take a long time (I already spent a couple hours fighting with parts of the build system, and almost made no advances at all). And what would that ultimately tell me?  The browsers will be changing their performance characteristics in this area, I'm sure.
